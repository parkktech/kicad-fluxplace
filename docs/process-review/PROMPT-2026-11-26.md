# Process review prompt (2026-11-26, owner request)

Self-contained prompt for an outside reviewer (or a Fable review) of the fluxplace board-building process.
Context: W16 UTV comms bridge (CM5 carrier), session 5. Answers go to `docs/process-review/`; accepted items
become ledger rows + fix items (ONE-SHOT-LEDGER, LEDGER-AUDIT).

---

You are reviewing an automated PCB layout pipeline ("fluxplace") and the process used to drive it. I want concrete, prioritized advice on how to make it reach a fab-ready board faster and more reliably. Be specific; challenge the architecture where it is wrong.

## Context
- Board: 6-layer (Sig/GND/Sig/Sig/GND/Sig) carrier for a Raspberry Pi CM5, ~345 parts, ~700 connections. High-speed: PCIe Gen2 x1 + refclk and USB3 to an M.2 Key B modem, 4 Ethernet pairs + 4 line-side pairs through magnetics, USB2 hub/USB-C; 4 Bluetooth modules + GNSS + SMA RF (50 ohm, outer layers); several power rails (VBATT_IN/VBATT_PROT up to ~5 A, VMODEM, +5V, +3V3); audio/analog pairs through transformers. KiCad 10, routers: KiCadRoutingTools ("KRT", grid router) first, Freerouting as fallback.
- Pipeline ("constructive flow"), one Python process, stages in order: ready (parts/datasheets/models) -> modules -> floorplan (placement + gap->repair loop with "rungs") -> fanout -> pour-tie -> placetour (placement tournament judged by a quick "ghost" KRT route) -> lookahead -> pairs (differential pair layer) -> tune (skew) -> critroute (RF/clock nets) -> plan-route -> route (planes, power rails, pair groups, diff, RF, plain KRT, snap) -> close (repair loop: rip/reroute/widen rungs, guarded by DRC/score) -> trace-finish -> silk -> review (final hard gate: DRC + ~60 design checks + datasheet evidence).
- Every stage has a gate; a guard refuses edits that raise opens/shorts/DRC errors or change protected (locked) copper.
- Process: a top-level AI plans and reviews; worker AIs implement each fix on a git branch with tests; a merge gate runs the full test suite (~3100 tests, 20-30 min) and refuses any new failure; each fix is proven on the real board; every failure gets a row in a ledger (issue / cause / fix / measured result).

## Measured progress (this board)
- Placement accepted (0 KiCad errors). First full route: 452 -> 39 opens, 0 shorts. Best now: 22 opens, 0 shorts, 7 DRC errors (track not centred on via).
- Final review preview on the best board: 281 FAIL: silk 186 (silk stage not yet run), unrouted 23, power width 5 rails, datasheet-evidence 21 (now 3), RF traces at 71 ohm on inner layers instead of 50 ohm outer (4), decoupling caps 16-56 mm from their pins (10), crystal/RF/clock nets over length budget (9), Ethernet/PCIe skew over limit (5).

## Recurring failure patterns (please analyse these)
1. Regressions: an audit found only 41 of 119 logged failures were fixed in the automated flow with a test; the rest lived in hand scripts or one-off fixes and recurred (e.g. a thermal solder-mask window caused the same 203 errors on two board versions).
2. Fixes that pass unit tests and the merge gate but break the real flow in combination (e.g. a power-rail widening step modified locked copper and the stage's commit guard refused the whole route; a pcbnew Remove() corrupted SWIG state for later stages). Real-board checks run outside the stage guard missed these.
3. Dead ends: stages that stop and wait for an AI answer ("packets", exit 5) with nothing in the flow to answer them.
4. Order/priority problems: pairs that fail once are pushed behind lower-priority pairs; fanout before pairs scatters connector escapes; the plain router routes RF and power nets at default width when the specialised step fails.
5. Measurement problems: a quick-route judge whose result depended on the footprint order in the file; a power check charging every branch with the full rail current; stale reports that said pairs were unrouted when they were routed.
6. Placement problems that only show up at review (decaps far, crystals far, RF lengths), long after placement was accepted.
7. Slow iteration: one full route run takes 2-3 h; the pairs stage alone 12-107 min; each fix needs a 20-30 min test gate.

## Questions
A. Architecture: is a strictly sequential stage pipeline with per-stage gates the right shape? Should placement be judged by full routability (and review checks) before it is accepted, and how cheaply? What should run in which order (pairs vs fanout vs rails vs RF)?
B. What invariant checks or contracts would catch problems 2, 4 and 5 automatically (e.g. "no stage may route a net class at default width", "report must equal board", "deterministic judge")?
C. How to make the repair/close loop actually converge instead of refusing every candidate (score design, guard design, multi-objective acceptance)?
D. How to cut iteration time: incremental routing, caching, checking only the touched region, smaller real-board checks that still run through the stage guards?
E. How to stop regressions structurally: what should the test suite contain beyond unit tests (golden boards, end-to-end stage tests, property tests)?
F. Where would a commercial autorouter / placer workflow (or published research on PCB placement and routing) do this differently, and what is worth borrowing?
G. Anything in the process (AI-driven fix loop, ledger, merge gate) you would change.

Give a prioritized list (top 10) with the expected impact and effort for each, then details.
